# مدل دامنه و منابع حقیقت هم‌ساخت

این سند مرجع مشترک محصول، داده و محاسبات است. هدف آن جدا نگه‌داشتن
«مشارکت»، «اجرای پروژه»، «مالی»، «مالکیت» و «حاکمیت» و در عین حال تعریف
پیوندهای کنترل‌شده میان آن‌هاست.

## ساختار مالکیت داده

```text
سازمان
├── اعضای سازمان، دعوت‌ها، API key و اتصال‌ها
├── پروفایل عمومی و تنظیمات اعلان
└── پروژه‌ها
    ├── اعضای پروژه و دسترسی‌ها
    ├── نیازها و پیشنهادهای همکاری
    ├── عملیات، بودجه، ریسک و KPI
    ├── حسابداری، پرداخت، توزیع و ارزش‌گذاری
    ├── ذی‌نفعان، دفتر سهم و اقدامات شرکتی
    ├── جلسات، مصوبات و اقدام‌های پیگیری
    ├── قالب و اجرای آمادگی بهره‌برداری
    └── اسناد، نظرات، گزارش و listing بازار
```

همهٔ داده‌های پروژه‌ای با `projectId` و سازمان مالک آن محدود می‌شوند. دسترسی
به یک پروژه، به معنی دسترسی به پروژه‌های دیگر همان سازمان نیست مگر نقش
سازمانی کاربر چنین اختیاری بدهد.

## هویت، نشست و RBAC

هویت کاربر مستقل از عضویت است. یک کاربر می‌تواند در چند سازمان و پروژه با
نقش‌های متفاوت عضو باشد.

- نقش سازمانی: `owner`، `admin`، `project_manager`، `finance`، `board`،
  `auditor` و `viewer`
- نقش پروژه‌ای: `project_manager`، `contributor`، `finance`، `board`،
  `auditor` و `viewer`
- مجوز مؤثر برابر اجتماع مجوز نقش سازمانی و نقش پروژه‌ای است.
- `viewer` سازمان فقط metadata سازمان را می‌بیند؛ مشاهدهٔ پروژه برای او
  نیازمند عضویت صریح پروژه است.
- دعوت می‌تواند سازمانی یا مختص یک پروژه باشد.
- نشست مرورگر با رمز و در صورت فعال‌بودن MFA با TOTP یا backup code صادر
  می‌شود.
- API key به سازمان، سازنده و scope محدود است؛ تعلیق کاربر یا عضویت، کلید را
  بی‌اعتبار می‌کند.

جزئیات سیاست دسترسی و کنترل‌های امنیتی در [SECURITY.md](SECURITY.md) آمده است.

## مشارکت عمومی

نیاز، ظرفیت یا آورده‌ای است که پروژه برای تحقق خود طلب می‌کند. پیشنهاد،
پاسخ خصوصی یک فرد یا مجموعه به همان نیاز است.

وضعیت مشتق‌شدهٔ نیاز:

| وضعیت | قاعده |
|---|---|
| `open` | پیشنهاد فعال ندارد |
| `under_review` | پیشنهاد `new` یا `contacted` دارد |
| `negotiating` | پیشنهاد در مذاکره دارد |
| `committed` | دقیقاً یک پیشنهاد پذیرفته‌شده دارد |

گردش اصلی پیشنهاد:

```text
new → contacted → negotiating → accepted
                           └──→ rejected
rejected → بازگشایی
accepted → لغو کنترل‌شده با ثبت تاریخچه
```

برای هر نیاز حداکثر یک پیشنهاد `accepted` مجاز است. پیشرفت مشارکت از فرمول
زیر می‌آید و follow/interest در آن نقشی ندارد:

```text
participationProgress =
  تعداد نیازهای فعال دارای پیشنهاد accepted / تعداد کل نیازهای فعال
```

توکن پیگیری فقط یک بار به متقاضی نشان داده می‌شود و hash آن در پایگاه داده
نگهداری می‌شود. API عمومی نام، موبایل، ایمیل و متن خصوصی پیشنهاد را افشا
نمی‌کند.

## اجرای پروژه

مدل عملیات مستقل از جذب مشارکت است:

- فاز شامل زمان‌بندی، وزن، وضعیت و پیشرفت مشتق‌شده از فعالیت‌هاست.
- فعالیت می‌تواند parent، فاز، مسئول، وابستگی، وزن، تاریخ، زمان ثبت‌شده و
  درصد پیشرفت داشته باشد.
- وابستگی چرخه‌ای و تخصیص بیش از ظرفیت منابع کنترل می‌شود.
- ریسک و مسئله، احتمال، اثر، band، مالک و برنامهٔ پاسخ دارند.
- KPI دارای مقدار هدف، جهت مطلوب، دوره و measurementهای تاریخ‌دار است.
- progress update روایت مدیریتی یک وضعیت را نگهداری می‌کند.

منبع پیشرفت اجرایی:

1. اگر فاز فعال وجود داشته باشد، میانگین پیشرفت فازهای فعال؛
2. در غیر این صورت، میانگین وزن‌دار فعالیت‌های سطح بالای فعال؛
3. اگر هنوز دادهٔ عملیات وجود نداشته باشد، نماهای سازگاری می‌توانند fallback
   مشارکت/هدف را صریح نمایش دهند، اما آن را دادهٔ عملیات معرفی نمی‌کنند.

بودجه نسخه‌دار است. فقط نسخهٔ `approved` بودجهٔ جاری گزارش می‌شود و بازنگری،
نسخه‌ای تازه می‌سازد؛ تاریخچهٔ نسخه‌های قبلی حذف نمی‌شود.

## موتور آمادگی بهره‌برداری

رسیدن مشارکت به ۱۰۰٪ به‌تنهایی پروژه را عملیاتی نمی‌کند. «آمادگی
بهره‌برداری» یک دروازهٔ مستقل میان قطعی‌شدن مشارکت و شروع عملیات واقعی است.

ساختار داده:

```text
قالب سازمانی (نوع پروژه / صنعت / نسخه)
└── مراحل مرتب‌شده
    ├── نوع اقدام: دستی، فرم، سند، وظیفه یا مصوبه
    ├── فرم پویا و فیلدهای اعتبارسنجی‌شده
    ├── قواعد عبور
    └── تأیید یک‌مرحله‌ای یا ارسال و تأیید مدیر

پروژه
└── اجرای snapshotشدهٔ قالب
    ├── پاسخ‌ها و سند شاهد
    ├── وضعیت هر مرحله و تأییدکنندگان
    └── تاریخچهٔ append-only رویدادها
```

قواعد declarative فعلی عبارت‌اند از:

| نوع | منبع حقیقت |
|---|---|
| `manual_checkbox` | مقدار boolean فیلد فرم snapshotشده |
| `form_field` | پاسخ فرم با عملگرهای `eq/neq/filled/true/gte/lte/in` |
| `document_exists` | سند فعال همان پروژه با حداقل یک نسخه و دستهٔ اختیاری |
| `task_status` | وظیفهٔ غیرآرشیوی همان پروژه با وضعیت `done` |
| `resolution_approved` | مصوبهٔ بسته با outcome تصویب‌شده و حدنصاب معتبر |

شرط نهایی:

```text
eligibleToOperate =
  (participationRequired ? activeCommittedNeeds = activeNeeds > 0 : true)
  AND requiredSteps > 0
  AND every required step is completed/waived
  AND every gate rule currently passes
```

قالب و اجرای پروژه دو موجودیت متفاوت‌اند. هنگام initialize، نام و نسخهٔ قالب،
مرحله‌ها، فرم‌ها و قواعد snapshot می‌شوند؛ بنابراین تغییر قالب فقط پروژه‌های
بعدی را تحت تأثیر قرار می‌دهد. فعال‌سازی در یک transaction وضعیت اجرای
آمادگی و `projects.lifecycle/stage` را به `operating` می‌برد. API عمومی و
ویرایش معمول پروژه اجازهٔ دورزدن این transaction را ندارند. خروج از
بهره‌برداری نیز به ثبت دلیل و عملیات `suspend` نیاز دارد.

اگر مشارکت یا یک قاعدهٔ بیرونی پس از فعال‌سازی نامعتبر شود، وضعیت مؤثر
`attention_required` است. سامانه به‌طور خودکار تصمیم حقوقی/عملیاتی قبلی را
پاک نمی‌کند؛ مدیر باید پس از بررسی، مشکل را رفع یا بهره‌برداری را رسماً متوقف
کند.

هر تغییر پروژه‌ای فرایند، پس از commit، یک پیام SSE عمومی و تجمیعی منتشر
می‌کند. این پیام برای invalidate/refresh نماهاست و عمداً پاسخ فرم، یادداشت،
عامل انسانی و سند شاهد را حمل نمی‌کند.

## حسابداری و عملکرد مالی

### دفتر کل دوطرفه

منبع حقیقت مالی، `journal_entries` و `journal_lines` است. هر سند قبل از ثبت
قطعی باید تراز باشد و هر خط دقیقاً بدهکار یا بستانکار است. گزارش‌ها فقط
اسناد `posted` و `reversed` را در نظر می‌گیرند.

```text
سود خالص = درآمد ثبت‌شده - هزینهٔ ثبت‌شده
حاشیه سود = سود خالص / درآمد
Profit ROI = سود خالص / سرمایهٔ مستند
```

سند ثبت‌شده ویرایش یا حذف نمی‌شود؛ اصلاح با reversal انجام می‌گیرد. بستن دورهٔ
مالی، ثبت در آن بازه را محدود می‌کند و بازگشایی یک عملیات مدیریتی قابل ممیزی
است.

### فاکتور، پرداخت و توزیع

- فاکتور فروش/خرید می‌تواند سند حسابداری متناظر بسازد و ابطال آن رویداد
  جبرانی ایجاد می‌کند.
- payment intent در حالت production فقط `manual` است تا هیچ ورودی کاربر
  نتواند موفقیت provider واقعی را جعل کند.
- توزیع سود ابتدا preview و allocation می‌سازد، سپس تصویب و پرداخت می‌شود.
- الزام KYC توزیع از پیکربندی سرور می‌آید و body درخواست قادر به خاموش‌کردن
  آن نیست.

### ارزش‌گذاری و بازده

ارزش‌گذاری فعلی دستی و صریح است و می‌تواند به سند پشتیبان پیوند بخورد.
بازده از جریان‌های ثبت‌شده محاسبه می‌شود:

- سرمایهٔ مستند: خالص خطوط حساب حقوق مالکانه با `systemKey=capital`
- توزیع: allocationهای `approved/processing/paid`
- ارزش پایانی: آخرین valuation در تاریخ گزارش
- بازده ذی‌نفع: سرمایهٔ tagشده به ذی‌نفع، توزیع او و سهم وی از ارزش‌گذاری بر
  اساس دفتر سهم در تاریخ ارزش‌گذاری
- XIRR: برآورد سالانه از تاریخ و مبلغ جریان‌ها، نه تضمین بازده

اگر سرمایه، جریان با علامت مخالف، valuation یا دادهٔ مالکیت کافی نباشد،
سامانه عدد ساختگی نمی‌سازد و علت unavailable را برمی‌گرداند.

## سرمایه، cap table و انتقال

ذی‌نفع ممکن است شخص یا سازمان باشد. اطلاعات هویتی و تماس او خصوصی است.

موجودی سهم یک فیلد قابل ویرایش نیست:

```text
موجودی هر ذی‌نفع در هر طبقه =
  مجموع issuance و transfer_in و adjustment مثبت
  - مجموع transfer_out و adjustment منفی
```

cap table، درصد مالکیت و قدرت رأی از دفترکل سهم مشتق می‌شوند. رویداد دفترکل
حذف نمی‌شود. انتقال فقط پس از کنترل تعلق طرفین به پروژه، طبقهٔ سهم، موجودی
فروشنده و وضعیت درخواست روی دفترکل اثر می‌گذارد.

پس از bootstrap مالک، تأیید انتقال علاوه بر کنترل‌های موجودی به شواهد زیر
وابسته است:

1. مصوبه متعلق به همان پروژه، جلسهٔ `held`، وضعیت `closed`، حد نصاب برقرار و
   outcome برابر `approved`؛ scope ساختاری آن باید دقیقاً رده، طرفین، تعداد،
   مبلغ و ارز همین انتقال را پوشش دهد و فقط برای یک عملیات مصرف می‌شود؛
2. KYC معتبر و منقضی‌نشده برای فروشنده و خریدار؛
3. قرارداد `active` همان پروژه و سازمان که هر دو ذی‌نفع را به‌عنوان طرف
   قرارداد دارد؛ برای معاملهٔ مبلغ‌دار، ارز قرارداد باید ارز پروژه و ارزش آن
   حداقل مبلغ معامله باشد؛
4. برای قیمت بزرگ‌تر از صفر، payment intent ورودی `succeeded`، مستقل از
   invoice و با purpose غیرقابل‌تغییر `share_transfer/<transferId>`، ارز و مبلغ
   دقیقاً برابر معامله؛ یک payment نمی‌تواند دو انتقال را پوشش دهد؛
5. ثبت درخواست و تأیید آن توسط دو کاربر فعال متفاوت.

گردش enterprise به‌صورت
`draft → pending → approved/rejected/cancelled` است. همهٔ mutationهای این چرخه
به نشست تعاملی نیاز دارند و فقط سازنده می‌تواند شواهد draft خود را تکمیل و
ارسال کند؛ API key حق ساخت، ارسال، تأیید، رد یا لغو انتقال را ندارد. شواهد در
لحظهٔ تأیید، داخل همان transaction کنترل موجودی و ثبت دو طرف دفترکل دوباره
اعتبارسنجی می‌شوند. انتقال با قیمت صفر از الزام payment معاف است، اما مصوبه،
KYC، قرارداد و four-eyes همچنان لازم‌اند.

### اقدام شرکتی

انواع اجرایی نسخهٔ فعلی:

- `issuance`
- `capital_increase`
- `split`
- `reverse_split`
- `rights_issue`

پس از bootstrap مالک، هر اقدام تغییردهندهٔ سرمایه باید:

1. به مصوبهٔ همان پروژه با scope ساختاری دقیق نوع اقدام، رده، تعداد/نسبت،
   ذی‌نفع و تاریخ‌های مؤثر متصل باشد؛ هر مصوبه فقط یک بار bind/consume می‌شود؛
2. جلسهٔ مصوبه `held`، مصوبه `closed`، حد نصاب برقرار و نتیجه `approved` باشد؛
3. توسط کاربر فعال سازمان ساخته شود؛
4. توسط شخصی غیر از سازنده تصویب شود؛
5. توسط شخصی غیر از سازنده اجرا شود؛
6. هنگام اجرا همان preview و شواهد مصوبهٔ زمان تصویب را داشته باشد.

بنابراین صدور مستقیم endpoint سازگاری legacy پس از bootstrap با
`CORPORATE_ACTION_REQUIRED` رد می‌شود. «four-eyes» در این نسخه جدایی سازنده
از تصویب‌کننده و اجراکننده است؛ الزام سه شخص کاملاً مجزا تعریف نشده است.

ثبت داخلی سهم جایگزین سند حقوقی، احراز هویت رسمی، قرارداد انتقال یا ثبت نزد
مرجع قانونی نیست.

## حاکمیت و تصمیم

جلسه، حاضرین، مصوبات، proxy، رأی و نتیجه را نگهداری می‌کند. وزن رأی از snapshot
دفتر سهم و قواعد عضو هیئت‌مدیره محاسبه می‌شود تا تغییر مالکیت بعدی نتیجهٔ
تاریخی را عوض نکند. نتیجهٔ نهایی شامل حد نصاب و outcome است.

ذی‌نفع حقیقی می‌تواند به یک کاربر فعال همان سازمان متصل شود و این اتصال در هر
پروژه یکتا است. در سازمان bootstrap‌شده رأی فقط توسط همان کاربر لینک‌شده یا
کاربری ثبت می‌شود که ذی‌نفع او proxy فعال و معتبر جلسه/مصوبه است؛ API key و
مدیر حاکمیت نمی‌توانند با ارسال یک `stakeholderId` دلخواه به‌جای سهام‌دار رأی
بدهند. رأی، کاربر ثبت‌کننده و شناسهٔ proxy را در snapshot نگه می‌دارد.

ساخت و لغو proxy نیز فقط توسط نشست تعاملی همان کاربر لینک‌شده به ذی‌نفع
اعطاکننده مجاز است. چون هر ذی‌نفع در مدل فعلی یک رأی واحد روی هر مصوبه دارد،
رأی شکسته پشتیبانی نمی‌شود و proxy باید تمام قدرت رأی اعطاکننده را منتقل کند.
نهایی‌سازی، tally و حدنصاب را محاسبه و همراه `result_json` و وضعیت `closed` در
یک تراکنش ثبت می‌کند؛ بنابراین پس از مشاهدهٔ نتیجه رأی تازه‌ای وارد نمی‌شود.

هر مصوبه می‌تواند action item داشته باشد:

```text
open → in_progress → blocked → completed
  └───────────────→ cancelled
completed/cancelled → open
```

اقدام دارای مسئول فعال سازمان، موعد، اولویت، جلسه و مصوبهٔ مرتبط است. هر
transition تاریخچهٔ before/after و پیوند hash به audit سراسری دارد.

## اسناد و همکاری

- سند metadata، دسته، visibility و status دارد.
- هر upload نسخهٔ تازه با SHA-256 می‌سازد؛ نسخهٔ قبلی بازنویسی نمی‌شود.
- visibility خصوصی با permission و دستهٔ سند دوباره کنترل می‌شود.
- سند می‌تواند به منبعی مانند قرارداد، جلسه یا رویداد مالی link شود.
- comment به `resourceType/resourceId` متصل است و مشاهدهٔ comment منبع خصوصی
  از دسترسی به خود منبع تبعیت می‌کند.

محتوای سند به‌صورت BLOB در SQLite ذخیره و همراه backup نگهداری می‌شود. فایل‌ها
رمزنگاری سراسری در سطح برنامه ندارند؛ حفاظت at-rest بر عهدهٔ دیسک/volume و
backup رمز‌شدهٔ محیط است.

سهمیهٔ سازمان، پروژه، تعداد نسخه و نرخ ساعتی upload قابل تنظیم است و کنترل
اندازه/سهمیه در transaction انجام می‌شود تا ارسال هم‌زمان از سقف عبور نکند.

## اعلان، اتصال و marketplace

- notification داخل برنامه برای کاربر نگهداری می‌شود.
- preference کانال/رویداد ذخیره و از API قابل تنظیم است؛ در نسخهٔ فعلی همهٔ
  تولیدکننده‌های outbox هنوز این preferenceها را هنگام enqueue اعمال نمی‌کنند.
- outbox payload حساس را sealed نگه می‌دارد و هیچ API سازمانی payload یا لینک
  bearer دعوت/بازنشانی را reveal نمی‌کند.
- جداول هویت فقط hash توکن را دارند، اما لینک bearer برای تحویل تا حذف outbox
  به‌صورت AES-GCM sealed در SQLite و backup قابل‌بازیابی است. تحویل دستی فقط
  با ابزار اپراتوری محلی و انتخاب صریح یک رکورد انجام می‌شود.
- وضعیت‌های دستی ارسال، retry و cancel قابل ممیزی‌اند؛ worker رکورد processing
  رهاشده را پس از lease بازیابی می‌کند و با compare-and-swap اجازه نمی‌دهد
  پاسخ دیررس provider یک رکورد لغوشده را دوباره sent/pending کند.
- integration connection تنظیمات رمز‌شده و حالت `manual/sandbox/live` دارد،
  اما مقدار `live` به‌تنهایی adapter یا موفقیت اتصال بیرونی ایجاد نمی‌کند.
- outbox خودکار فعلی عمدتاً دعوت و بازنشانی رمز را پوشش می‌دهد؛ اعلان‌های
  دامنه‌ای مالی، عملیات و حاکمیت به‌صورت کامل به آن متصل نشده‌اند.
- marketplace فعلی discovery است: listing عمومی، facet، جست‌وجو و saved
  listing. سفارش، escrow، clearing و settlement در آن وجود ندارد.

## audit و سازگاری

رویدادهای enterprise به زنجیرهٔ HMAC متصل‌اند و before/after، actor، پروژه،
سازمان و request id را با redaction کلیدهای حساس ثبت می‌کنند. اعتبار زنجیره از
API سازمانی قابل بررسی است. این کنترل tamper-evident است، نه WORM بیرونی؛ کلید
HMAC باید جدا از backup داده محافظت شود.

APIهای `v1` برای صفحهٔ عمومی و مهاجرت داده حفظ شده‌اند. مسیر اصلی مدیریت
محصول `v2` است. پس از ساخت مالک، نشست مدیریت legacy غیرفعال می‌شود و عملیات
حساس سرمایه و ثبت مالی تک‌طرفه از مسیر legacy مجاز نیست. دادهٔ مالی legacy
برای مهاجرت و مشاهده باقی می‌ماند؛ منبع حقیقت مالی فقط journal دوبل است.

## اصول یکپارچگی

- عملیات چندمرحله‌ای مالی، سرمایه و وضعیت در transaction انجام می‌شوند.
- mutationهای حساس از idempotency key استفاده می‌کنند؛ تکرار همان درخواست
  نتیجهٔ قبلی و تغییر payload با همان کلید خطای conflict می‌دهد.
- شناسه و scope هر منبع پیش از mutation دوباره با پروژه و سازمان کنترل می‌شود.
- مبالغ و واحد سهم عدد صحیح امن‌اند؛ aggregate خارج از محدوده رد می‌شود.
- داده‌های immutable با delete یا update اصلاح نمی‌شوند؛ رویداد جبرانی ثبت
  می‌شود.
- صفحهٔ عمومی فقط دادهٔ صریحاً عمومی یا تجمیعی را دریافت می‌کند.
- API key نمی‌تواند چرخهٔ ساخت و ابطال API key را به‌جای نشست تعاملی انجام دهد.
- API key هویت سازنده را فقط برای attribution دارد و shortcut مالک/نویسندهٔ
  سند و comment خصوصی را از نشست انسانی او به ارث نمی‌برد.
