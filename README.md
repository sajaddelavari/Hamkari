# هم‌ساخت

پلتفرم سبک و فارسی برای مدیریت سبد پروژه‌ها، مشارکت‌ها، سرمایه، عملکرد مالی،
تحقق اهداف و حاکمیت پروژه.

هم‌ساخت چهار تجربهٔ یکپارچه دارد:

- پرتفوی عمومی و اتاق مستقل هر پروژه
- فرم پیشنهاد و لینک خصوصی پیگیری
- بازار فرصت‌های همکاری و سرمایه‌گذاری
- فضای کاری سازمانی برای مدیریت کامل اجرا، مالی، سرمایه، اسناد و حاکمیت

پیشرفت اجرایی، در صورت وجود دادهٔ عملیات، از فازها و وظایف وزن‌دار محاسبه
می‌شود؛ در نبود آن از اهداف و در نهایت از تکمیل مشارکت به‌عنوان fallback صریح
استفاده می‌شود. تکمیل مشارکت شاخص مستقلی از نیازهایی است که پیشنهادشان رسماً
پذیرفته شده است؛ دنبال‌کردن و اعلام علاقه صرفاً شاخص تعامل‌اند.

ماژول‌های نسخهٔ ۳:

- چندسازمانی، چندپروژه‌ای، عضویت سازمان/پروژه و RBAC
- حساب شخصی، نشست hashشده، TOTP MFA، کد بازیابی، دعوت و API key محدود
- جذب مشارکت و گردش بررسی پیشنهادها
- فاز، وظیفه، وابستگی، زمان، منابع، ریسک، KPI، هدف و بودجهٔ نسخه‌بندی‌شده
- موتور آمادگی بهره‌برداری با قالب سازمانی، فرم پویا، قواعد قابل ارزیابی و دروازهٔ مشارکت ۱۰۰٪
- حسابداری دوبل، دورهٔ مالی، سند و reversal، فاکتور، پرداخت و توزیع سود
- ارزش‌گذاری، سود و زیان، ROI و XIRR با اعلام صریح دادهٔ ناکافی
- ذی‌نفع، طبقهٔ سهام، cap table، عرضه، انتقال، حق‌تقدم و گواهی سهام
- جلسه، حضور، وکالت، رأی وزن‌دار، مصوبه و پیگیری «مصوبه تا اقدام»
- KYC و امضای دستیِ قابل ممیزی، قرارداد، سند نسخه‌بندی‌شده و نظر
- اعلان، outbox دستی، گزارش CSV/HTML/JSON، marketplace و audit زنجیره‌ای HMAC

تعاریف دقیق محاسبات و مرزهای هر دامنه در
[مدل عملیاتی پلتفرم](docs/PLATFORM_MODEL.md) ثبت شده است.
آخرین وضعیت تحویل، کنترل کیفیت و آمادگی استقرار نیز در
[گزارش وضعیت محصول](docs/STATUS_REPORT.md) نگهداری می‌شود.
برای استقرار و کنترل‌های امنیتی به
[راهنمای استقرار](docs/DEPLOYMENT.md)، [مدل امنیت](docs/SECURITY.md) و
[نقشه API](docs/API.md) مراجعه کنید.

## اجرای توسعه

نیازمندی‌ها:

- Node.js 24 یا بالاتر
- npm

```bash
npm install
npm run dev
```

سپس این نشانی‌ها در دسترس‌اند:

- صفحه عمومی: `http://localhost:3000`
- فضای کاری اصلی: `http://localhost:3000/workspace`
- بازار فرصت‌ها: `http://localhost:3000/marketplace`
- پنل قدیمی مهاجرت: `http://localhost:3000/admin`
- سلامت سرویس: `http://localhost:3000/healthz`

در محیط توسعه، اگر `ADMIN_PASSWORD_HASH` یا `ADMIN_DEV_PASSWORD` تنظیم نشده باشد، برنامه در هر اجرا یک رمز موقت تصادفی می‌سازد و در log آغاز سرویس نشان می‌دهد. برای داشتن رمز ثابت محلی می‌توانید `ADMIN_DEV_PASSWORD` با حداقل ۱۲ نویسه تنظیم کنید. این fallback در محیط production غیرفعال است.

## تنظیم محیط production

فایل نمونه را کپی کنید:

```bash
umask 077
cp .env.example .env
chmod 600 .env
test "$(stat -c '%a' .env)" = "600"
test "$(stat -c '%u' .env)" = "$(id -u)"
```

دو دستور `test` باید بدون خطا تمام شوند؛ در غیر این صورت پیش از درج رازها،
مالکیت فایل را به کاربر استقرار برگردانید و مجوز آن را اصلاح کنید.

برای ساخت hash رمز مدیر، فرمان زیر را اجرا و رمز را در prompt مخفی وارد کنید:

```bash
npm run hash-password
```

برای اجرای خودکار نیز می‌توان رمز را از متغیر موقت `ADMIN_PASSWORD` یا stdin فرستاد؛ آن را به‌عنوان آرگومان فرمان ننویسید، چون ممکن است در history یا فهرست processها بماند. خروجی را در `ADMIN_PASSWORD_HASH` و داخل کوتیشن تکی قرار دهید تا علامت‌های `$` توسط Docker Compose تفسیر نشوند. `SESSION_SECRET` نیز باید یک مقدار تصادفی منحصربه‌فرد با حداقل ۳۲ نویسه باشد (برای نمونه خروجی `openssl rand -base64 48`). placeholder فایل نمونه عمداً نامعتبر است تا production با secret پیش‌فرض بالا نیاید.

متغیرهای اصلی:

| متغیر | توضیح |
|---|---|
| `NODE_ENV` | در production دقیقاً `production` |
| `PUBLIC_ORIGIN` | origin عمومی، مانند `https://ham.example.com` |
| `ADMIN_PASSWORD_HASH` | hash تولیدشده با دستور بالا |
| `SESSION_SECRET` | راز session و امضای شناسه ناشناس |
| `AUTH_ENCRYPTION_KEY` | کلید مستقل رمزگذاری MFA، تنظیمات provider و payload اعلان |
| `AUDIT_HMAC_KEY` | کلید مستقل زنجیرهٔ HMAC برای آشکارسازی دست‌کاری؛ این کنترل WORM نیست |
| `DATA_DIR` | پوشه پایدار SQLite؛ پیش‌فرض محلی `./data` |
| `BACKUP_DIR` | پوشه خروجی backup؛ در Docker برابر `/app/backups` |
| `DATABASE_PATH` | مسیر صریح فایل دیتابیس؛ `:memory:` فقط در development/test و در production ممنوع است |
| `TRUST_PROXY` | `false` برای دسترسی مستقیم؛ IP/CIDR پراکسی معتمد برای استقرار پشت reverse proxy |
| `NOTIFICATION_PROVIDER` | فقط `manual` یا در محیط غیر production مقدار `sandbox` |
| `PAYMENT_PROVIDER_MODE` | فقط `manual` یا در محیط غیر production مقدار `sandbox` |
| `DISTRIBUTION_KYC_REQUIRED` | در production باید `true` بماند |
| `PORT` | پورت HTTP؛ پیش‌فرض `3000` |

پشت reverse proxy فقط IP یا CIDR همان پراکسی را در `TRUST_PROXY` قرار دهید (برای نمونه `172.16.0.0/12`). مقدار عمومی `true` در production عمداً پذیرفته نمی‌شود تا هدر جعلی `X-Forwarded-For` نتواند محدودسازی درخواست‌ها را دور بزند.

## Docker

```bash
docker compose up -d --build
```

داده‌های SQLite در volume نام‌دار `hamsakht-data` و snapshotها در `hamsakht-backups` نگهداری می‌شوند. برنامه داخل کانتینر با کاربر غیر root اجرا می‌شود و Docker healthcheck مسیر `/healthz` را بررسی می‌کند. فایل‌های دیتابیس و backup روی میزبان‌های POSIX با دسترسی `0600` و پوشه‌هایشان با `0700` ساخته می‌شوند.

پیش از اولین اجرای production، `.env` را با مقادیر واقعی تکمیل کنید.

دیتابیس خالی در development با یک پرتفوی نمونه از پروژه‌های کشاورزی، انرژی و
فناوری پر می‌شود تا تمام ماژول‌ها قابل آزمایش باشند. در production هیچ دادهٔ
نمایشی ساخته یا منتشر نمی‌شود؛ اولین اجرا فقط یک پروژهٔ خالی با وضعیت `draft`
می‌سازد تا مدیر اطلاعات واقعی را تکمیل و سپس منتشر کند.

## مدل گردش‌کار مشارکت

وضعیت پیشنهاد:

```text
new → contacted → negotiating → accepted
                         └────→ rejected
```

پیشنهاد ردشده قابل بازگشایی است. لغو یک پذیرش نیازمند تأیید مدیر و در تاریخچه ثبت می‌شود.

وضعیت نیاز از پیشنهادهایش مشتق می‌شود:

| کلید | معنی |
|---|---|
| `open` | پیشنهاد فعالی ندارد |
| `under_review` | پیشنهاد جدید یا تماس‌گرفته‌شده دارد |
| `negotiating` | مذاکره در جریان است |
| `committed` | یک پیشنهاد پذیرفته شده است |

برای هر نیاز تنها یک پیشنهاد می‌تواند هم‌زمان پذیرفته باشد.

## اجرا، مالکیت، مالی و حاکمیت

- موجودی سهام از دفترکل رویدادهای صدور و انتقال محاسبه می‌شود و فیلد قابل‌ویرایش
  مستقیمی برای موجودی وجود ندارد.
- پس از ساخت نخستین مالک سازمان، صدور مستقیم قدیمی غیرفعال است. تغییر سرمایه
  فقط با اقدام شرکتی، مصوبهٔ تصویب‌شده و کنترل دو نفره انجام می‌شود؛ سازنده
  نمی‌تواند همان اقدام را تصویب یا اجرا کند.
- انتقال در مسیر `draft → pending → approved/rejected/cancelled` حرکت می‌کند و
  تمام تغییر وضعیت‌های آن فقط با نشست تعاملی مجاز است. فقط سازنده می‌تواند
  شواهد پیش‌نویس خود را تکمیل کند و تنها تأیید کاربر دوم، پس از کنترل موجودی،
  KYC دو طرف، قرارداد فعال، مصوبهٔ scoped یک‌بارمصرف و پرداخت purpose-bound
  (برای معاملهٔ مبلغ‌دار)، cap table را تغییر می‌دهد.
- عرضهٔ خرید یا فروش می‌تواند به انتقال مرتبط شود و ماندهٔ عرضه پس از تأیید
  انتقال به‌صورت اتمیک کم می‌شود.
- سند مالی پس از posting تغییرناپذیر است. اشتباه با reversal جبران می‌شود،
  تراز بدهکار/بستانکار اجباری است و دورهٔ بسته‌شده mutation نمی‌پذیرد.
- پیشرفت عملیاتی از فازها و وظایف وزن‌دار محاسبه می‌شود. تکمیل مشارکت، تحقق
  KPI/اهداف و عملکرد مالی شاخص‌های مستقل و دارای منبع دادهٔ روشن‌اند.
- جلسه، حاضران، مصوبه، نتیجه و رأی وزن‌دار سابقهٔ مستقل دارند. فقط مواردی که
  مدیر برای انتشار علامت زده است در صفحهٔ عمومی دیده می‌شوند.
- وضعیت مصوبه فقط در مسیر `draft → open → closed` جلو می‌رود. هنگام وجود
  مصوبهٔ باز، صدور سهم، تأیید انتقال، تغییر وزن رأی و تغییر فهرست افراد واجد
  رأی تا بسته‌شدن رأی‌گیری قفل می‌شوند تا یک واحد سهم نتواند دوبار رأی بدهد.
  عضو فعال هیئت‌مدیرهٔ بدون سهام یک رأی پایه دارد؛ سایر رأی‌دهندگان به قدرت
  رأی مشتق‌شده از دفتر سهام نیاز دارند.
- رأی فقط توسط کاربر لینک‌شده به ذی‌نفع یا نمایندهٔ دارای proxy معتبر ثبت
  می‌شود. مدیر یا API key نمی‌تواند با شناسهٔ دلخواه به‌جای سهام‌دار رأی بدهد.
  وکالت نیز فقط توسط حساب تعاملی متصل به اعطاکننده ساخته/لغو می‌شود و به‌دلیل
  پشتیبانی‌نشدن رأی شکسته، تمام قدرت رأی او را در دامنهٔ جلسه یا مصوبه منتقل
  می‌کند. نتیجه و بسته‌شدن مصوبه در یک تراکنش ثبت می‌شوند.
- ثبت مالی تک‌طرفهٔ legacy پس از bootstrap فقط خواندنی است؛ گزارش و mutation
  مالی جدید فقط از journal دوبل و دورهٔ مالی کنترل‌شده استفاده می‌کند.

## آمادگی و شروع بهره‌برداری

- مدیر سازمان برای نوع پروژه یا صنعت، قالب فرایند قابل استفاده مجدد می‌سازد و
  ترتیب مراحل، الزامی/اختیاری‌بودن و نیاز به تأیید جداگانهٔ مدیر را تعیین می‌کند.
- هر مرحله می‌تواند فرم پویا با متن، عدد، تاریخ، انتخاب و چک‌باکس داشته باشد و
  شرط عبور آن به پاسخ فرم، سند دارای نسخه، وظیفهٔ تکمیل‌شده یا مصوبهٔ تصویب‌شده
  با حدنصاب متصل شود.
- آغاز فرایند برای پروژه، یک snapshot نسخه‌دار از قالب می‌سازد؛ ویرایش بعدی
  قالب، سابقه و شروط پروژهٔ در حال اجرا را تغییر نمی‌دهد.
- بهره‌برداری فقط هنگامی فعال می‌شود که مشارکت همهٔ نیازهای فعال قطعی، همهٔ
  مراحل الزامی کامل و تمام قواعد در لحظهٔ تصمیم معتبر باشند. تغییر مستقیم
  `lifecycle/stage` به `operating` با خطای `READINESS_REQUIRED` رد می‌شود.
- اگر شرطی پس از شروع بهره‌برداری از اعتبار بیفتد، سامانه وضعیت
  `attention_required` نشان می‌دهد؛ توقف بهره‌برداری فقط با نشست تعاملی مدیر،
  ثبت دلیل و تاریخچهٔ ممیزی انجام می‌شود.

KYC، امضا و پرداخت داخلی در این نسخه «گردش ثبت دستی و قابل ممیزی» هستند و
موفقیت provider خارجی جعل نمی‌شود. اتصال بانکی، احراز هویت رسمی، امضای معتبر
حقوقی و ثبت نزد مراجع قانونی به adapter و قرارداد سرویس واقعی در استقرار مقصد
نیاز دارد.

## API

API عمومی:

- `GET /api/v1/projects`
- `GET /api/v1/projects/current`
- `GET /api/v1/projects/:slug`
- `PUT /api/v1/needs/:id/viewer-state`
- `POST /api/v1/needs/:id/proposals`
- `GET /api/v1/proposals/track` با هدر `Authorization: Bearer <token>`
- `GET /api/v1/projects/:slug/events`

API اصلی سازمانی زیر `/api/v2` قرار دارد و از session شخصی/CSRF یا API key
محدود استفاده می‌کند. ورودی فضای کاری `GET /api/v2/admin/workspace` است و
منابع هر پروژه زیر `/api/v2/admin/projects/:projectId` قرار دارند؛ از جمله:

- عملیات: `phases`، `tasks`، `dependencies`، `time-entries`، `resources`،
  `allocations`، `risks`، `kpis`، `goals` و `budgets`
- مالی: `accounts`، `fiscal-periods`، `journal-entries`، `invoices`،
  `payment-intents`، `distributions`، `valuations` و `reports/returns`
- سرمایه و حقوقی: `stakeholders`، `share-classes`، `share-offers`،
  `share-transfers`، `corporate-actions`، `preemptive-rights`،
  `share-certificates`، `kyc-cases` و `contracts`
- حاکمیت و دانش: `meetings`، `decision-actions`، `documents` و `comments`
- آمادگی بهره‌برداری: `readiness`، قالب‌های سازمانی، مراحل، فرم‌ها، ارزیابی،
  فعال‌سازی و توقف کنترل‌شده

مسیرهای `/api/v1/admin` فقط برای مهاجرت قبل از bootstrap حفظ شده‌اند و پس از
ساخت مالک سازمان با `LEGACY_ADMIN_DISABLED` غیرفعال می‌شوند. صدور مستقیم
قدیمی نیز پس از bootstrap با `CORPORATE_ACTION_REQUIRED` رد می‌شود.
عملیات حساس صدور سهم، ثبت عرضه، درخواست انتقال و ثبت مالی به هدر تصادفی
`Idempotency-Key` با طول ۳۲ تا ۱۲۸ نویسه نیاز دارند. تکرار دقیق همان درخواست،
پاسخ قبلی را برمی‌گرداند و استفادهٔ همان کلید برای payload متفاوت با خطای
`409 IDEMPOTENCY_CONFLICT` رد می‌شود.

پاسخ خطا شکل ثابتی دارد:

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "اطلاعات ورودی معتبر نیست.",
    "fields": {
      "mobile": "شماره موبایل معتبر وارد کنید."
    }
  },
  "requestId": "..."
}
```

## تحویل دستی اعلان‌های احراز هویت

در production هیچ API مدیریتی لینک دعوت یا بازنشانی را برنمی‌گرداند. اپراتور
مجاز روی خود سرور ابتدا فقط metadata صف را می‌بیند و سپس یک شناسهٔ دقیق را
به‌صورت تعاملی تحویل می‌گیرد:

```bash
docker compose exec hamsakht npm run notification:manual -- list
docker compose exec hamsakht \
  npm run notification:manual -- deliver <OUTBOX_ID>
```

فرمان دوم پس از تأیید، فقط همان پیام را رمزگشایی و رکورد را اتمیک `sent`
می‌کند؛ خروجی شامل لینک bearer حساس است و نباید در log، ticket یا history
ذخیره شود. این وضعیت به معنی تحویل ایمیل خارجی نیست؛ اپراتور باید همان لحظه
پیام را از کانال امن مصوب ارسال کند. اگر خروجی از دست رفت، reset/دعوت تازه
بسازید؛ ابزار همان رکورد را دوباره reveal نمی‌کند.

## پایگاه داده و backup

SQLite در حالت WAL اجرا می‌شود. migrationها با `PRAGMA user_version` اعمال و
دیتابیس نسخه prototype نیز بدون حذف داده تا schema فعلی ارتقا داده می‌شود.

ساخت backup:

```bash
npm run backup
```

خروجی JSON شامل مسیر، اندازه و `sha256` snapshot است؛ مقدار hash را همراه زمان
backup در سامانهٔ پایش یا محل خارج از سرور ثبت کنید.

در Docker:

```bash
docker compose exec hamsakht npm run backup
```

برای کپی snapshotها به پوشه‌ای خارج از volume:

```bash
docker compose cp hamsakht:/app/backups ./backups
```

خروجی backup را خارج از سرور نیز نگهداری کنید. این نسخه برای اجرای تک‌نمونه‌ای طراحی شده و نباید چند کانتینر هم‌زمان را روی یک فایل SQLite اجرا کرد.

## تست و کنترل کیفیت

```bash
npm run check
npm run test:backend
npx playwright install chromium
npm run test:e2e
npm run audit:lighthouse
```

تست‌ها migrationهای قدیمی و میان‌نسخه‌ای، transaction، اعتبارسنجی، احراز هویت،
حریم خصوصی، idempotency عملیات حساس، کنترل موجودی و طرفین انتقال، تغییر وضعیت
پیشنهاد و مسیر کامل ثبت تا پذیرش را پوشش می‌دهند. تست مرورگر همچنین RTL،
دسترس‌پذیری، baseline تصویری، پرتفوی چندپروژه‌ای و چیدمان responsive را بررسی
می‌کند. ممیزی Lighthouse با پروفایل رسمی Desktop Dense‑4G و سه اجرای مستقل،
بودجهٔ Performance، Accessibility، Best Practices و SEO حداقل ۹۵، میانهٔ LCP
کمتر از ۲٫۵ ثانیه و بیشترین CLS کمتر از ۰٫۱ را enforce می‌کند؛ در صورت پیدا
نشدن خودکار Chrome می‌توانید مسیر آن را در `CHROME_PATH` بگذارید.

## ساختار

```text
server.js            نقطه شروع سرویس
src/                 config، migration، storeهای دامنه، routeها، security و SSE
public/              رابط عمومی و پنل مدیر
scripts/             ابزار hash رمز، تحویل دستی اعلان، backup، restore، syntax و Lighthouse
docs/                مدل دامنه، API، امنیت، استقرار و گزارش وضعیت
test/                تست‌های backend و مرورگر
data/                دیتابیس محلی؛ در Git ذخیره نمی‌شود
```

## حریم خصوصی

نام، موبایل، ایمیل و متن پیشنهاد فقط برای actor دارای
`proposals.read_sensitive` در scope همان پروژه قابل مشاهده‌اند. صفحه عمومی
صرفاً وضعیت و آمار تجمیعی را نمایش می‌دهد. لینک پیگیری token تصادفی را فقط در
fragment نگه می‌دارد، رابط وب آن را پس از import از address bar پاک می‌کند و
درخواست وضعیت آن را در هدر می‌فرستد تا در access log پراکسی ثبت نشود. token
خام نیز در دیتابیس ذخیره نمی‌شود.

فونت محلی [Vazirmatn](https://github.com/rastikerdar/vazirmatn) تحت مجوز OFL 1.1 در `public/assets/fonts` قرار دارد.
